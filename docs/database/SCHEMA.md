# PAWS Firestore Schema

**Database:** `vista-teaching-lab` (Firestore Native, `northamerica-northeast1` / Montreal)
**Purpose:** isolated development, test and CI database. Synthetic data only.
**Canonical rules:** `firebase/firestore.rules` · **Indexes:** `firebase/firestore.indexes.json`

This document is the authoritative description of the data model. Every collection,
field, type and invariant listed here is enforced by `firebase/firestore.rules` and/or
validated by `tests/seed-dataset.test.js`.

> **Privacy invariant.** No real staff data may ever be written to this database.
> Everything below is generated by `tools/seed/dataset.js` from a fixed seed.

---

## 1. Design principles

1. **Source / mirror split.** `sessions` holds the private source of truth.
   `calendar_sessions` is a public, allowlisted projection of it. The two must be
   field-equal after every write — enforced by `calendarMatchesSourceAfter()`.
2. **Private request split.** A change request is split across five collections so
   that each office sees only its own scope: public request, workflow routing,
   per-office approvals, private faculty target, append-only audit.
3. **Derived data is disposable.** `settings/*` indexes are rebuildable from
   `sessions` + `faculty`. Nothing authoritative lives there.
4. **Sanitized projections over broad reads.** Where a role needs to reference
   another person, it reads a sanitized derived document, never `/faculty` and
   never a raw `/users` list.
5. **Audit is append-only.** Every `*_log` / `*_audit` collection denies
   `update` and `delete` outright.

## 2. Identity

### `users/{uid}`

The account record. One document per Firebase Auth user.

**Access:** `get` is limited to the account holder and administrators; `list` is
Owner-only. Faculty-role accounts that need to reference a colleague read
`settings/people_index` (§8) instead. This closes the enumeration gap where any
faculty account could previously read every colleague's name, email, `facultyId`,
`active` flag and password-change state.

| Field | Type | Notes |
| --- | --- | --- |
| `name` | string | display name |
| `email` | string | institutional address |
| `role` | string | one of the explicit roles below |
| `facultyRoles` | list\<string\> | 1–3 of `hicc`, `visc`, `faculty`; forbidden on office accounts |
| `facultyId` | string | required when `role` is faculty-linked; must exist in `/faculty` |
| `active` | bool | inactive accounts fail every `ready()` check |
| `mustChangePassword` | bool | see §7 — UI guidance only, not a security control |
| `officeName` | string | ADFA/ADC/LAB display name, office accounts only |
| `officeEmail` | string | office accounts only |
| `updatedBy` / `updatedByName` | string | actor stamp |
| `updatedAt` / `createdAt` | timestamp | server time |

**Explicit roles:** `owner`, `administrator`, `other_office`, `adfa_general`,
`adfa_regular`, `admin`, `editor`, `viewer`, `hicc`, `visc`, `faculty`, `adc`, `lab`.

**Role → office mapping** (`officeForRole`): `adc`→ADC, `lab`→LAB,
`owner`/`administrator`/`admin`/`adfa_general`/`adfa_regular`→ADFA, everything else→none.

### `faculty/{facultyId}`

The Faculty Directory record. **Read access is restricted**: `admin()` or the
owner of the record (`ownFacultyId`). Ordinary faculty never read this collection
for anyone but themselves.

| Group | Fields |
| --- | --- |
| Identity | `firstName`, `lastName`, `email`, `ucid` |
| Appointment | `appointmentType`, `rank`, `currentTitle`, `expiryDate`, `fte` |
| Contract DOE | `doe`, `doeTeaching`, `teachingDOE`, `contractTeachingDOE` |
| Override | `doeOverride2026_27` (map: `value`, `reason`, `notes`), `overrideDOE`, `overrideReason` |
| Derived | `teachingDoeModel2026_27`, `assignedTeachingDOE`, `doeAssignedTeachingDOE`, `teachingSummary2026_27` |
| Roles | `managedRoles2026_27`, `roleMigration2026_27` |
| Availability | `awayFromCampusRecords`, `awayFromCampusSource`, `awayFromCampusImportedAt`, `awayFromCampusImportedBy` |
| Summary import | `facultySummary2026_27`, `facultySummarySource2026_27`, `facultySummaryStatus2026_27`, `facultySummaryImportedAt`, `facultySummaryImportedBy` |
| Workload policy | `workloadPolicy2026_27`, `workloadPolicySource2026_27`, `workloadPolicyImportedAt2026_27`, `workloadPolicyImportedBy2026_27` |
| Provenance | `bulkImportedAt`, `bulkImportedBy`, `updatedBy`, `updatedByName`, `updatedAt` |

**DOE resolution order** (`web/js/faculty/faculty-doe.js`): approved override → contract DOE →
`null` (never silently zero). When a policy bundle is supplied the canonical
engine is used instead and the result carries `policyVersionId`, `ruleId`, `ruleKey`.

### `faculty_groups/{groupId}`

HICC-owned swap groups. `name`, `ownerUid`, `courseIds`, `memberUids`,
`updatedBy`, `updatedByName`, `updatedAt`, `createdAt`.
Invariant: `ownerUid` must be an active `hicc` account and must be a member.

during calendar repair.

## 4. Multi-office change approval

A routed request is one logical change spread over five collections.

### `change_requests/{requestId}` — public half
`requestSchema` (`office-routing-v1`), `requesterUid`, `requesterName`,
`requesterRole`, `sessionId`, `requestType` (`session_edit` | `faculty_swap`),
`scope`, `groupId`, `groupName`, `status`, `revision`, `basePublic`, `patchPublic`
(both restricted to the public session field set), `currentFacultyName`,
`proposedFacultyName`, `editableFields`, `requesterMessage`, `reason`, `course`,
`date`, `topic`, `requestedAt`, `updatedAt`, `withdrawnBy`, `withdrawnAt`,
`appliedRevision`, `appliedAt`.

**Status machine:** `pending` → (`update_required` → `pending`) → `approved`
→ applied · or → `rejected` · or → `withdrawn`.

### `change_request_workflow/{requestId}` — routing
`requestId`, `revision`, `requiredOffices` (subset of `adc`,`lab`,`adfa`),
`hasFacultyChange`, `finalType`, `scopes` (office → field list),
`scopeSignatures` (office → signature), `updatedAt`.

### `change_request_approvals/{requestId}_{office}` — per-office decision
`requestId`, `office`, `revision`, `fields`, `scopeSignature`, `status`,
`decidedBy`, `decidedByName`, `decidedAt`, `message`, `updatedAt`.

**Invariant:** a decision only counts when `status == 'approved'` **and** `fields`
and `scopeSignature` still match the workflow. Changing a draft invalidates prior
approvals by changing the signature — approvals are never silently reused.

### `change_request_private/{requestId}` — private target
`requestId`, `requesterUid`, `revision`, `assignmentChange`
(`assignmentIndex`, `from` / `to` each `{facultyId, candidateKey, kind}`),
`updatedAt`. Readable by ADFA approvers only.

### `change_request_audit/{requestId}` — append-only
`requestId`, `event`, `revision`, `status`, `office`, `message`,
`changedFields`, `changedBy`, `changedByName`, `changedAt`.
`update`/`delete` denied.

**Spark constraint.** A request containing a faculty change must be finalised by
ADFA after the other required offices approve — there is no server-side
transaction available on the Spark plan. Migration marker:
`UCVM_DB_MIGRATION_REVISIT: spark-client-finalizer`.

### `workflow_notifications/{id}`
`recipientOffice`, `kind` (`request_assigned`, `request_resubmitted`,
`office_decision`, `request_applied`, `request_withdrawn`,
`assignment_recheck_required`), `requestId`, `sessionId`, `course`, `date`,
`start`, `end`, `type`, `topic`, `facultyDisplayName`, `message`, `createdAt`,
`readBy` (starts empty; only the reader's own uid may be appended).

## 5. Faculty workload (DOE) and AFC

### `afc_requests/{requestId}`
`requesterUid`, `facultyId`, `reportToUid`, `status`, `workDays`, `startDate`,
`endDate`, `appointmentType`, `rank`, `reason`, `purposeDestination`, `coverage`,
`facultyName`, `reportsTo`, `contactAddress`, `contactPhone`,
`applicantSignature` (`uid`, `attested`, `signedAt`), `reportToSignature`,
`adminSignature`, `rejectionReason`, `withdrawnBy`, `withdrawnAt`,
`pdfChunkCount`, `pdfSha256`, `pdfByteLength`, `submittedAt`, `approvedAt`,
`updatedAt`.

**Status machine:** `pending_report_to` → `pending_admin` → `approved` ·
or → `rejected` · or → `withdrawn`.

**Privacy:** another faculty member may learn only binary availability
(`Available` / `Unavailable`). Never the reason, never the date range.

### `afc_requests/{requestId}/pdf_chunks/{index}`
`index`, `base64`, `sha256`. Creatable only while the parent is `approved` and
only when `sha256` matches the parent's `pdfSha256`. Immutable afterwards.

### `afc_audit/{id}` — append-only
`changedBy`, `changedAt`, `action`, `requesterUid`, `reportToUid`, plus context.

## 6. Derived data (`settings/*`)

All rebuildable. `web/js/data-index/index-maintenance.js` owns the rebuild.

| Document | Visibility | Contents |
| --- | --- | --- |
| `settings/system_state` | all ready users (read) | write lock: `teachingDataWriteLocked`, `maintenanceMode`, `activeImportId`, `maintenanceOwnerUid`, `maintenanceOwnerName`, `maintenanceStartedAt`, `lastCompletedImportId`, `lastCompletedAt` |
| `settings/faculty_index` | admin | sanitized faculty search index |
| `settings/schedule_stats` | admin | per-course/term aggregates |
| `settings/faculty_swap_index` | ready non-office | **sanitized** swap candidates — see §8 |
| `settings/faculty_swap_map` | admin | private key → `facultyId` resolution |
| `settings/faculty_summary_2026_27` | general | 2026-27 summary import |

**System-state lock protocol.** Acquiring the write lock requires an existing
`bulk_import_jobs/{id}` in `APPLYING` owned by the same actor. Releasing it
requires that job to have reached `COMPLETED` or `RESTORED`. This makes an
interrupted import recoverable rather than permanently locking teaching writes.

## 8. Sanitized swap-candidate projection

This is the model that lets a faculty member reference a colleague without
reading `/faculty` or listing `/users`.

**`settings/faculty_swap_index`** — readable by any ready non-office account.
Contains **only**:

| Field | Notes |
| --- | --- |
| `entries[].key` | opaque candidate key (not a UCID, not a uid) |
| `entries[].name` | display name only |
| `entries[].unavailableRanges` | **coarse** availability windows, no reason |
| `entries[].conflicts` | course + time only, which timetable users already see |
| `generatedAt` | rebuild stamp |

**Forbidden in this document:** `ucid`, `email`, `facultyId`, any DOE value, any
AFC reason, any HR field.

**`settings/faculty_swap_map`** — admin-only. Maps `key` → `facultyId` so ADFA can
resolve a sanitized key at approval time and re-check live availability before
applying.

### `settings/people_index` — HICC people picker projection

Added to close the `/users` enumeration gap. The HICC group-swap picker needs to
offer colleague names, but it previously read `/users` directly, which also
exposed `email`, `facultyId` and account state.

| Field | Notes |
| --- | --- |
| `entries[].uid` | account uid |
| `entries[].name` | display name |
| `entries[].role` | `hicc` / `visc` / `faculty` only |
| `generatedAt` | rebuild stamp |

**Forbidden:** `email`, `facultyId`, `active`, `mustChangePassword`, office fields.
Readable by ready faculty-role accounts; writable by ADFA admin only.

## 11. Known limitations

These are recorded rather than hidden. Each is tracked in the audit report.

1. **`mustChangePassword` is self-cleared.** `selfPasswordCompletion()` lets the
   account holder flip it. It is UI guidance, not a control. Do not rely on it.
   Replacing it with a trusted invitation or institutional SSO is still open.
2. **Rule evaluation budget is close to Firestore's 1000-expression ceiling.**
   Adding further `getAfter()`/`existsAfter()` calls requires an evaluation-cost
   review first. `tests/rules-evaluation-budget.test.js` pins the current count.
3. **Spark plan has no server-side transaction**, hence the client-side finaliser
   and its migration marker.
4. **The legacy request shape is still writable.** A pre-routing request can still
   be approved, but only when the paired session write happens in the same commit
   (`legacyAppliedCompanionWrite`). The shape should eventually be retired once no
   pre-routing records remain.

## DOE authoritative model and write boundary

DOE is split into policy/configuration, source facts, derived evidence and audit collections. The browser may read only the subsets allowed by `firebase/firestore.rules`; authoritative mutation is performed by trusted admin tooling.

| Collection | Purpose | Browser write |
| --- | --- | --- |
| `doe_policies` | academic-year policy identity and active-version pointer | denied |
| `doe_policy_versions` | immutable/reviewed policy versions and draft state | denied |
| `doe_rules` | canonical DOE calculation rules | denied |
| `doe_rule_selectors` | rule matching selectors | denied |
| `doe_rule_inputs` | named calculation inputs | denied |
| `doe_rule_parameters` | rule parameters/constants | denied |
| `doe_rule_tiers` | tiered calculation bands | denied |
| `doe_reference_sources` | source/reference evidence | denied |
| `doe_course_mappings` | course-to-policy mappings | denied |
| `doe_subject_mappings` | subject-to-policy mappings | denied |
| `doe_exceptions` | approved policy exceptions | denied |
| `doe_faculty_targets` | annual faculty DOE target overrides/evidence | denied except through trusted server/admin boundary |
| `doe_assignments` | canonical DOE assignment facts | fully denied to browser |
| `doe_calculation_records` | calculation result/provenance records | denied |
| `doe_impact_runs` | policy impact-preview run summaries | denied |
| `doe_impact_rows` | impact-preview per-faculty rows | denied |
| `doe_publications` | publication evidence | denied |
| `doe_recalculation_requests` | **non-authoritative** request to recalculate the current DOE-bearing session facts | DOE administrators may create strict `pending` requests only; browser update/delete denied |
| `doe_recalculation_batches` | controlled recalculation progress/evidence | denied |
| `doe_audit_log` | append-only authoritative DOE audit | denied |

`doe_recalculation_requests` is intentionally outside the authoritative-result set. When a Firebase-only browser save changes a session with faculty assignments, the client strips DOE result/provenance fields from the submitted assignments and creates a strict `pending` request in the same Firestore batch as the source session/calendar write. The request contains no new DOE value, rule result, policy result, or calculation evidence.

The trusted admin job re-reads the **current** session before recalculating, derives the current assignment scope, resolves the current Active policy for that Academic Year, and writes authoritative DOE results/evidence through the existing server services. A stale queued request therefore cannot force an old assignment index back onto a newer session state. Failed requests remain `pending` with retry metadata.

The active test writer is `.github/workflows/firebase-doe-admin.yml`, which authenticates to the isolated `vista-teaching-lab` project using a GitHub Environment secret and invokes the existing server-side DOE services. Because Firebase Admin SDK access is outside client Security Rules, the workflow itself is guarded by manual dispatch, a hard project-id lock and typed confirmation for destructive operations.

Legacy fields such as `facultySummary2026_27`, `managedRoles2026_27` and `workloadPolicy2026_27` remain migration/source evidence only. New authoritative DOE state belongs in the canonical DOE collections above.

**Source:** Beta PR #150 (documentation reconciliation), PR #151 (Withdraw / Withdrawn wording), PR #152 (UX-07 AFC date edit; SQL migration 064). **Target when implemented:** isolated `vista-teaching-lab` Firestore. **Implementation state:** proposed contract only. The default PAWS GitHub Pages Testing site uses browser-local synthetic records, not live Firestore; its AFC date edits do not prove Firestore persistence or security.

### PR #150 and #151: no database migration

PR #150 contains documentation and repository-maintenance changes. In this repository, retain the environment/role boundaries of `PAWS_CONSTITUTION.md`, `docs/architecture/testing-environments.md`, and `docs/security/role-matrix.md`; do not copy Beta SQL runtime assumptions into the Firestore Lab. PR #151 changes administrator AFC record wording from Delete / Archived / Inactive to Withdraw / Withdrawn, but the underlying state remains `active: false`. **Legacy ambiguity:** historical records with `active: false` might have been merely disabled; do not rewrite them as proven user withdrawals or fabricate an actor/time.

### PR #152: proposed fields and collections

Retain the current `afc_requests/{requestId}` structure, append-only `afc_audit`, and immutable original PDF chunks. When a real trusted Firestore implementation is approved, extend each request with:

| Field | Type | Proposed purpose |
| --- | --- | --- |
| `versionToken` | string (16 uppercase hex) or server-managed monotonic revision | Optimistic concurrency; cannot be supplied as a new request's authoritative version by an arbitrary client |
| `replacesAfcRequestId` | string or null | On a new Faculty date-change request, links to the original approved request |
| `replacesVersion` | string or null, private/server-managed | Snapshot of original revision at submission, rechecked at final approval |
| `supersededByAfcRequestId` | string or null | On prior approved request after a linked replacement is finally approved |
| `teachingSessionsSnapshot` | bounded list/map, private | Derived from the faculty's teaching assignments in the *new* date interval; no personal data in public projections |
| `dateChangeAuditRef` | string or null | Optional reference to immutable before/after audit evidence |
| `status` extension | `superseded` | Terminal state for a *previously approved* request whose linked replacement was approved |

For authorized *manual/imported* AFC record sources, keep stable IDs and `active`; propose `versionToken` / `updatedAt` fields and an append-only `afc_dates_changed` audit event for direct ADFAD edits. Do not automatically reinterpret or overwrite historical `active:false` records.

### Proposed transaction and authorization invariants

1. **Faculty date-change submission:** only the active request owner, only from `approved` and not already superseded; validate full new AFC form/terms/signature, expected original revision, valid working dates, new coverage and real teaching conflicts. Reject duplicates if a linked date change is pending. Create a *new* request in `pending_report_to` or `pending_admin` using the currently authorized Reports-To mapping. Leave the old approved dates and availability untouched.
2. **Final approval:** require the authorized current approver and a matching original revision; in a single trusted transaction approve the replacement, mark the old request `superseded`, update the private active-availability projection to the new range, and append **before/after** events. If a revision, approval, identity or scope changed, reject without a partial update. A rejection/withdrawal of the replacement leaves the old approved interval active.
3. **ADFAD direct approved-request edit:** only active ADFAD administrators; require an exact original version and no pending replacement; validate new dates and *recompute* teaching conflicts/coverage before changing the active interval. In one transaction update the request and derived availability, bump revision and append `afc_dates_changed` with actor/time/original/new dates. Never silently carry stale `teachingSessionsSnapshot` across a changed interval.
4. **Manual AFC record date edit:** similarly check source kind, active status, version and dates, then change the record and its approved availability projection atomically. Withdrawn records cannot be modified.
5. **Privacy and append-only evidence:** do not allow ordinary Faculty accounts to list another person's AFC reason, date range, contact information, signatures or PDF. Only owner, correctly assigned Reports-To and authorized ADFAD office may read detail; public timetable availability remains binary. `afc_audit` and original PDFs must not be edited or deleted. Preserve historical approved PDF bytes even when dates are superseded; a new approved PDF is a separately versioned artifact, never an overwrite.
6. **Backend enforcement:** implement these conditions in trusted transactions / reviewed Firestore rules and test deny cases with real Firebase Auth; the Pages Demo's role selector and localStorage are *not* proof of server authorization. Browser client cannot forge the original version, approve its own request or write audit/result collections directly.
7. **Indexes and budget:** before deployment, review indexes for (`replacesAfcRequestId`, `status`) and private authorized scope lists. Recalculate the Rules evaluation budget from `tests/rules-evaluation-budget.test.js`; reject a release that exceeds the evaluation limit.
8. **Acceptance:** synthetic-only fixtures; stale original revision, concurrent replacement, date move onto teaching, absent coverage, withdraw/reject preserving old dates, authorized ADFAD direct edit, unauthorized faculty denial, original PDF immutability, audit reconstruction, and non-mutation of `tester-teaching`/University SQL.

**Not executed:** Beta SQL `database/azure-sql/064_afc_date_edit.sql` and its rollback/acceptance scripts are SQL Server references only. They must **not** be run as Firestore migrations or copied verbatim into `firebase/firestore.rules`. A future Firestore implementation requires its own reviewed PR, deployment permission, rules/index tests, synthetic seed, rollback evidence and explicit approval.


## Planned Firestore Faculty future activation contract (Testing PR #99)

**Deployment scope:** The default PAWS Github Pages testing build uses `tools/pages-demo-api/` with synthetic `localStorage` data. These are future schema and rules recommendations, **not** applied Firestore migrations or deployed rules. SQL Beta PR #155 / SQL065 is only a reference.

### Proposed Faculty fields and status

- `faculty/{facultyId}.administrativeActive` (boolean, administrator-controlled), independent of appointment dates.
- `faculty/{facultyId}.activationDate` (nullable `YYYY-MM-DD` calendar date, campus-local America/Edmonton semantics).
- Derived `effectiveActive = administrativeActive && (activationDate == null || activationDate <= campusToday)`.
- Derived statuses are **Active**, **Pending Start** (administratively enabled but future activation), **Inactive** (manually disabled). Pending staff are not treated as manually disabled.
- Existing Faculty with no activation date preserve their existing active state. Do not rewrite historical assignment/DOE/AFC data to calculate a new status.

### Proposed trusted writes and validation

1. Authorized ADFAD administrator creates a new canonical Faculty document using a new immutable ID; keep professional profile linked by the same ID. A UCID or email is required; reject duplicates case-insensitively even if the previous record is inactive. Create an immutable audit event.
2. Date editing requires a version/revision check; reject moving the activation date after any existing related course, working revision, finalization or published schedule. Keep historical records and manual DOE overrides unchanged.
3. Manual deactivate changes the administrative enablement only, retaining Faculty ID, activation date, roles, DOE and relationships. Restore the same ID without bypassing the future start date.
4.
